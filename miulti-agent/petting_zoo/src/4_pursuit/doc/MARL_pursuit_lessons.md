## 1. 題材 — Pursuit はなぜ MARL の試験台になるのか

PettingZoo / SISL の **Pursuit** は、追跡者（pursuer）8体を操作し、ランダムに動く獲物（evader）30体を
囲い込んで捕まえる協調タスクである（環境仕様と実装方針は[第1回](https://yoshishinnze.hatenablog.com/entry/2026/06/07/043000)）。
前段の Wizard War やボクシングのような対戦型と違い、
**個々のエージェントのスタンドプレーでは上限が低く、チームとしての配置と役割分担が要求される**。
これがこの題材を選んだ理由であり、同時にこの題材を難しくしている理由でもある。

| 項目 | 仕様 |
|---|---|
| エージェント | pursuer 8体（学習対象）、evader 30体（ランダム方策） |
| 観測 | 各エージェント中心の 7×7×3 局所グリッド（壁・味方・敵） |
| 行動 | 上下左右＋停止（離散5行動） |
| 捕獲条件 | 獲物の周囲の移動可能マスを埋める。位置により**最大4体**（端3体、角2体） |
| 報酬 | 捕獲 +5.0（周囲のpursuerへ）、タッチ +0.01、毎ステップ -0.1（緊急度） |
| 終了 | 全獲物捕獲、または 500 サイクル |
| 実行モデル | AEC（エージェントを1体ずつ順番に実行） |

この仕様には、MARL の古典的な難所がほぼ全部入っている。

1. **信用割当（credit assignment）** — 捕獲はチームの成果だが、誰のどの動きが寄与したかは自明でない（[第7回](https://yoshishinnze.hatenablog.com/entry/2026/07/04/043000)）。
2. **部分観測とマルコフ性の喪失** — 7×7 の視界には、次の獲物も、マップ全体の味方配置も映らない（[第10回](https://yoshishinnze.hatenablog.com/entry/2026/07/25/043000)）。
3. **非定常性** — 自分が学習している間に対戦相手（味方）の方策も変わる（[第14回](https://yoshishinnze.hatenablog.com/entry/2026/08/22/043000)）。
4. **組合せ的な役割分担** — 誰がどの獲物を、どの方向から囲むかという割り当て問題（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。
5. **報酬の疎性と不連続性** — 捕獲は稀で、しかも捕獲した瞬間に目標が消える（[第8回](https://yoshishinnze.hatenablog.com/entry/2026/07/11/043000)）。

以下の実験群は、結局この5つと順番に格闘した記録だと言ってよい。

## 3. 教訓1 — 報酬は「設計」ではなく「検証」するもの

### 3.1 チーム報酬だけでは「サボり」が合理的になる

最初の実装は `shared_reward=True` のチーム報酬一本だった（[第1回](https://yoshishinnze.hatenablog.com/entry/2026/06/07/043000)）。結果は捕獲ゼロ、報酬 -100〜-150、
エントロピー 1.60 前後でほぼ動かない。記録ではこの原因を、[第7回](https://yoshishinnze.hatenablog.com/entry/2026/07/04/043000)で
**信用割当問題**として整理している。

- 誰か1〜2体が捕まえれば全員に +5 が入るなら、残りは動かずに待つ方が自分のリスクは低い。
- 遠くで味方が衝突しているだけで、良い包囲の信号がノイズに埋もれる。
- 8体が同時に正しい位置に動く「奇跡」が起きるまで、個々の正しい1ステップは強化されない。

これは探索不足ではなく、**与えられた目的関数に対する合理的な最適解**である。ここで重要なのは
「エージェントが怠惰だ」と結論しないことだ。怠惰は設計の帰結であって、性質ではない。

### 3.2 個人報酬を足すと、今度は「隣接」で満足する

チーム報酬＋距離報酬＋衝突ペナルティのハイブリッドに変えると（[第7回](https://yoshishinnze.hatenablog.com/entry/2026/07/04/043000)）、開始直後から敵に一直線に向かう
行動は出る。しかし次に現れたのは、**最寄りの敵にまとわりつくだけで包囲しない**という局所解だった。
[第8回](https://yoshishinnze.hatenablog.com/entry/2026/07/11/043000)の分析が鋭い。

> 敵の周囲に集まること自体は起きやすい。しかし「周囲を囲む」はレアである。
> 隣接するだけで弱い報酬が出るなら、個々は最寄りの敵に張り付くだけで満足してしまう。

そこで 2マス以内への接近、上下左右の十字配置、同一セルへの重複排除を足す（[第8回](https://yoshishinnze.hatenablog.com/entry/2026/07/11/043000)）。それでも包囲は出ず、
さらに**報酬ハックの危険**が指摘される。十字配置に毎ステップ 0.25 が入るなら、
「捕獲せずに囲み続ける」方が累積報酬が高くなりうる。これは実際に後の実験で別の形で現れる
（[第11回](https://yoshishinnze.hatenablog.com/entry/2026/08/01/043000)の「捕獲報酬のみ」実験で、エージェントは待ち構える戦略に落ちた）。

### 3.3 報酬設計の実務原則

この一連の失敗から、次の原則が導ける。

1. **チーム報酬は「目的」、個人報酬は「勾配」**。前者だけでは学習信号が薄まり、後者だけでは
   チーム目的から外れる（[第7回](https://yoshishinnze.hatenablog.com/entry/2026/07/04/043000)）。比率は固定値ではなく、学習初期は個人寄り、後半はチーム寄りに
   アニールする余地がある（[第12回](https://yoshishinnze.hatenablog.com/entry/2026/08/08/043000)で構想されている）。
2. **報酬を足したら、必ず「一番安い抜け道」を探す**。囲み続ける、往復する、端で待つ、など（[第8回](https://yoshishinnze.hatenablog.com/entry/2026/07/11/043000)）。
   ポテンシャルベース整形 `R = γΦ(s') − Φ(s)` は往復ハックを理論的に抑えるが、
   「留まる」「捕獲しない」は別途潰す必要がある。
3. **報酬の変更は比較可能性を壊す**。[第10回](https://yoshishinnze.hatenablog.com/entry/2026/07/25/043000)で報酬全体を 1/5、[第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000)でハイブリッド報酬を 0.05 倍に
   している。したがって**報酬の絶対値を横断比較してはいけない**。比較すべきは捕獲数、
   エントロピー、そして行動の質である。
4. **疎な報酬を「段階化」する**のは有効だが、段階の途中に「そこで止まる理由」を作らない（[第8回](https://yoshishinnze.hatenablog.com/entry/2026/07/11/043000)、[第11回](https://yoshishinnze.hatenablog.com/entry/2026/08/01/043000)）。

## 4. 教訓2 — 観測が学習の天井を決める

### 4.1 「動け」と罰しても、方向がなければ徘徊になる

フェーズVの中心的な発見はこれに尽きる。索敵フェーズで停滞に -0.1 を与え、移動に +0.05 を
与えても（[第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000)）、**7×7 の局所観測が空なら、モデルにとってはどちらへ動いても同じ**である。
結果として学習は「リスクの低い狭い範囲の徘徊」に収束する。

ここで効いたのが、**最寄りの未捕獲獲物への相対方向 `(dy, dx)` を観測に直接連結する**ことだった（[第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000)）。
環境の実座標という、観測には含まれない特権情報を使うが、これは CTDE（中央集権学習・分散実行）の
枠組みでは許容される。結果として、

- 報酬平均は 116.2 → 132.4 に改善（最大 223.9）
- 「偵察 → 集団で捕獲 → 敵が減ったら別エリアへ移動」という流れが確認された
- ただし捕獲数は 32.0 → 30.7 と横ばい

**報酬は上がったが捕獲は増えていない。** これは「意図を持った移動」は実現したが、それが
捕獲効率に変換されていないことを意味する。観測を足すだけでは次の壁（過密）は崩れない。

### 4.2 全員が同じ「最寄り」を見ると、全員が同じ場所に行く

方向情報を足した次の問題は、**8体全員が同じ計算式 `min(距離)` を使う**ことだった（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。
獲物が2体しか残っていない状況で5体にとって最寄りが同じなら、5体が同じ方向を指し、
もう1体は誰にも見られない。これは「居座り」というより「**目が向いていない敵の放置**」である。

この構造的欠陥に対して、[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)ではハンガリアン法で1体1獲物の割当を導入する。結果は

| 指標 | 前回 (1051–1100) | 今回 (1251–1300) | 変化 |
|---|---:|---:|---:|
| Reward 平均 | 132.37 | 141.53 | +6.9% |
| 捕獲数 平均 | 30.71 | 34.35 | +11.8% |
| Reward 標準偏差 | 40.58 | 45.88 | 悪化 |
| Entropy 平均 | 1.3755 | 1.2400 | -9.8% |
| 直近10エピソード Reward | 180.26 | 152.75 | **悪化** |
| 直近10エピソード 捕獲数 | 36.4 | 36.0 | 横ばい |

そして動画では**居座りが再発**した。著者自身が「失敗」と評価している（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。

原因として記録が挙げているのは2点で、どちらも本質的である。

1. **割当キャッシュの更新バグ** — `cycles` という属性は PettingZoo の Pursuit には存在せず、
   `getattr(..., 0)` が常に0を返すため、割当はエピソード開始時に一度計算されたきりになる。
   しかもキャッシュしているのは獲物IDではなく**その時点の座標**なので、動く獲物ではなく
   「開始時にいた古い座標」へ向かい続ける。
2. **1体1獲物の割当が捕獲条件と合っていない** — Pursuit の捕獲は2〜4体で囲むことで成立する。
   8体を8獲物に分散させると、誰も包囲を完成できない。

### 4.3 観測設計の原則

1. **「望ましい行動」を罰する前に、その行動を選ぶのに必要な情報が入力にあるか確認する。**
   方向情報がなければ、探索報酬はランダムウォークに報酬を払うだけになる（[第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000) → [第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000)）。
2. **特権情報は、報酬（Critic・シェイピング）と観測（Actor）で使い分ける。**
   実座標を報酬計算に使うのはCTDEの範囲内だが、Actorに渡さないならActorは学習できない。
3. **同じ情報を全員に渡すと、意思決定が同質化する。** 方向やターゲットを渡すなら、
   同時に「誰がどれを担当するか」という差を作る仕組み（割当、ID、順序、排他）が必要になる（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。
4. **観測次元を変えたら、生成側と参照側の全箇所を同時に直す。**[第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000)では `obs_dim`、スライス境界、
   `feature_fuse` の入力次元の3箇所を直している。1つでも漏れると次元不一致で落ちるか、
   方向ベクトルが行動履歴に混ざって静かに壊れる。

## 5. 教訓3 — 表現力の跳躍はあるが、万能薬ではない

### 5.1 CNN → Transformer は「質的な跳躍」だった

フェーズIIIで最も明確に効いた介入は、CNN から Transformer への置き換えである（[第9回](https://yoshishinnze.hatenablog.com/entry/2026/07/18/043000)）。
記録の仮説は明快だった。

- **CNN の局所性** — 3×3 / 5×5 のカーネルを積んでも、7×7 の端と端の関係が全結合層まで統合されにくい。
  結果として「目の前の敵」にしか反応できない。
- **並進対称性による位置の消失** — 「右2マス」と「右3マス」の区別が潰れる。包囲では1マスの差が致命的。
- **Transformer の全域注意と位置埋め込み** — 全マスのペア関係を一発で計算し、座標は埋め込みで厳密に保持する。

結果は、報酬の上昇とエントロピーの低下、そして**味方が寄っていき敵の周囲を囲む**という
定性変化だった。これは「報酬をいくらいじっても出なかった」ものが、表現力の変更で出た例である。
仮説が当たった稀有なケースであり、同時に**帰納バイアス（inductive bias）をタスクに合わせる重要性**を示している。

Pursuit が要求するのは、画像分類的な「何が写っているか」ではなく、
**「誰がどこにいて、どの方向が空いているか」という関係と座標**である。CNN は前者に強く、
後者に弱い。Transformer はその逆の性質を持つ。

### 5.2 MAT は理論的に強いが、今回の環境では決定的でなかった

続く[第11回](https://yoshishinnze.hatenablog.com/entry/2026/08/01/043000)では、MARL を系列モデリング問題として扱う **MAT（Multi-Agent Transformer）** を導入する
（背景となる論文解説は連載外の `12_Multi-Agent_Transformer.md`）。
動機は「Actor が今この瞬間の他エージェントの意思決定を見られない」ことの解消である。

$$\text{MAPPO: } \pi_i(a_i \mid o_i, \text{全員の直前行動}) \quad\longrightarrow\quad
\text{MAT: } \pi_i(a_i \mid o_1,\dots,o_8,\ a_1,\dots,a_{i-1})$$

MAT は multi-agent advantage decomposition により単調改善が理論的に保証され、
ベンチマークでも MAPPO を上回る報告がある。しかし今回の結果は、

- ロス・報酬とも MAPPO から決定的な改善は見られない
- エントロピーが波打つ（学習が不安定）
- 捕獲報酬のみに絞ると、**待ち構え型**（獲物が近づいたら捕まえる）に落ちる

だった。ここから得られる教訓は重要である。

> **理論的保証は「その目的関数と観測の下での最適化」を保証するだけで、
> 望ましい協調行動が現れることは保証しない。**

MAT の単調改善は、与えられた報酬と部分観測の範囲で成り立つ。報酬が「待つ方が得」なら、
理論通りに「待つ」方策へ単調に改善する。アーキテクチャは仮説空間を広げるが、
**目的関数と観測が間違っていれば、より効率的に間違った解へ収束する**。

## 6. 教訓4 — 同時決定をやめると協調が生まれる。ただし順序が新たなバイアスになる

### 6.1 他者の行動を入力にする（Action-in-Action）

[第10回](https://yoshishinnze.hatenablog.com/entry/2026/07/25/043000)では、捕獲直後の「まごまご」に対して、他エージェントの直前行動を観測に連結する。
これは暗黙的なコミュニケーションであり、次の3つの課題を同時に緩和する。

- **報酬の不連続** — 獲物が消えても、他者の行動は連続している。次の目標の手がかりになる。
- **AEC の過渡状態** — 環境更新と行動選択のタイミングがずれても、共通の文脈を保持できる。
- **部分観測** — 他者の行動を外部メモリとして使い、実質的なマルコフ性を回復する。

結果として、捕獲後の歩調が合い、ロスとエントロピーの低下も早くなった。ただし記録自身が
「指標で見ていないので断言できない」と留保している点は誠実である。

### 6.2 自己回帰デコードは「誰が先に決めるか」を設計変数にする

[第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000)の洞察は、実装の細部に見えて本質的である。MAT はエージェントを1体ずつ順番に決めるが、
初期実装では順序が常に `0→1→…→7` の固定だった。すると、

- 常に同じエージェントが「先に決める側」、別のエージェントが「後から従う側」という**固定された役割**を学習する。
- 捕獲直後のように「誰が次にどの獲物へ動くべきか」が変わる局面で、その固定役割が邪魔になる。

対策は、**実IDとデコード順序（スロット）を分離**し、`fixed` / `random` / `priority` を選べるようにすること。
`priority` は「最寄りの未捕獲ターゲットまでの距離が近い順」に決める。緊迫しているエージェントが
先に判断し、他がそれに合わせるという理想に近づける。

ここで忘れてはいけないのが**配線**である。自己回帰モデルでは「誰が誰の行動を見て決めたか」が
学習信号の意味を決める。rollout 時に使った順序をバッファに保存し、PPO 更新時にも**同じ順序を再生**しないと、
causal mask と行動の対応がずれて学習が破綻する（[第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000)）。実際、`order` をモデル・PPO・バッファ・学習ループの
全経路に通す修正が行われている。

結果は、報酬・捕獲数の向上、エントロピーの安定化、そして「一貫した意思で動く」動作だった。
ただし終盤の崩れも観察されている。

### 6.3 協調構造の設計原則

1. **「同時決定」か「逐次決定」かは、それ自体が協調の設計である。** 独立Actorは実装が簡単だが、
   役割の重複を構造的に許す（[第10回](https://yoshishinnze.hatenablog.com/entry/2026/07/25/043000)）。自己回帰は役割の重複を減らすが、順序バイアスを導入する（[第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000)）。
2. **対称性を破る仕組みを入れる**（ランダム順序、優先度、ID、排他報酬）。ただし
   **順序は推論時と学習時で完全に一致させる**。
3. **暗黙的コミュニケーション（行動履歴）は安価で効く。** 明示的な通信チャネルを設計する前に、
   直前の行動を入れるだけで部分観測と非定常性の一部は緩和できる。

## 7. 教訓5 — 非定常性と「学習信号の分配」

### 7.1 同時クリッピングは、遅れているエージェントを道連れにする

[第14回](https://yoshishinnze.hatenablog.com/entry/2026/08/22/043000)の指摘は、MARL の PPO 実装でありがちな落とし穴である。MAT の標準的な定式化では、
チーム全体の同時確率比率

$$r = \exp\left(\sum_i \log \pi_i^{\text{new}} - \sum_i \log \pi_i^{\text{old}}\right)$$

でクリップする。しかし7体がほぼ最適で1体だけ大きく方策を変える必要がある場合、
その1体の変化で同時比率がクリップ範囲を出て、**全エージェントのそのサンプルの学習信号が弱まる**。
「遅れている1体を強く学ばせたい」場面で、集団最適化がそれを抑制するというジレンマである。

対策として、エージェントごとの比率・アドバンテージで個別にクリップし、その平均を取る方式が
導入された（`use_individual_clipping`）。厳密な MAT の定式化からは外れるが、実務的には
「1体の大きな更新が他を止めない」効果が期待できる。結果は捕獲数こそ横ばいだが、
エントロピーが低下し、接近してからの捕獲速度が上がった。

> 補足: 連載外の TROLL 論文解説（`12_troll_implementation.md`）は、PPO のクリップが KL 信頼領域の粗い近似であり、
> 「クリップすると勾配が完全に落ちる」「KL の大きさ自体は保証しない」という問題を指摘している。
> トークンごとの KL 射影で置き換える発想は、この「信号が止まる」問題への別解として読める。
> 本ディレクトリでは実験未実施だが、クリッピング設計を考える際の参照点になる。

### 7.2 MoE は「役割の器」だが、collapse する

[第12回](https://yoshishinnze.hatenablog.com/entry/2026/08/08/043000)–[第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000)で MAT を MoE 化し、状況に応じた expert の使い分け（突撃役・包囲役・切り替え役）を狙う。
しかし[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)で、Top-1 ゲーティングに**負荷分散損失がない**ため、初期の僅かな偏りが自己強化される
「collapse」が起きている可能性が疑われる。

実際、ログを見ると `decoder.layers.0.moe` の Expert 2 は利用率 0.01（約0.7%）でほぼ休眠、
Expert 3 に 0.52（約52%）が集中していた。負荷分散損失（`aux_loss`）と gate への LayerNorm を入れると、

- Expert 2 は 0.09〜0.12 まで復調
- `moe_aux_loss` は 1.063 → 1.011
- 24個（6層×4expert）の利用点が理想点 (0.25, 0.25) 付近に収縮
- 学習性能も向上し、捕獲数 38 を記録

しかし、**待機型の行動は戻ってきた**。ここが重要な分岐点である。

> MoE collapse は実在した。しかし、それは「居座り」の主因ではなかった。

したがって、モデルの表現力をいくら均等化しても、**入力に「切り替えるべき状況」を認識する情報が
なければ行動は変わらない**。[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)の総括はこの仮説を強く支持している。

### 7.3 Cross-Attention のゲートは「相手を見る前に」決まってしまう

[第14回](https://yoshishinnze.hatenablog.com/entry/2026/08/22/043000)のもう一つの指摘は、Cross-Attention のゲートが `gate_proj(query)` として**自分自身の隠れ状態だけ**から
計算されていることだ。これでは「他のエージェントが今何をしているか」を見る前に、情報をどれだけ
取り入れるかが決まる。学習初期にゲートが0付近に飽和すると、**連携に必要な通信路がほぼ遮断されたまま
学習が進む**リスクがある。

対策は、ゲート入力を `query` と `memory` の要約（平均）の連結にする `GatedCrossAttention` の新設。
併せて、ゲート値の分布（平均・標準偏差・`near_zero_ratio`）を可視化するデバッグ関数も用意されている。
結果は劇的な改善ではなかったが、捕獲速度の向上とエントロピー低下が確認された。

### 7.4 非定常性への実務原則

1. **学習信号の分配を疑う。** 報酬の分配（credit assignment）だけでなく、**勾配の分配**も
   MARL では設計対象になる。同時クリップ、共有 Critic、パラメータ共有は、どこで信号を薄めるかを意識する（[第14回](https://yoshishinnze.hatenablog.com/entry/2026/08/22/043000)）。
2. **役割分担をモデルに任せるなら、collapsing を監視する。** expert 利用率、ゲート飽和率、
   ユニット利用率などの**内部指標をログに出す**。行動だけ見ていても原因は分からない（[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)）。
3. **非定常性は「相手をモデル化する」だけでは足りない。** 味方の方策変化に適応するには、
   入力（行動履歴）、構造（順序・attention）、学習信号（個別クリップ）の3方向から攻める。

## 8. 教訓6 — 局所解は「バグ」ではなく「その設計での最適解」

### 8.1 待つことが最適になる条件

[第11回](https://yoshishinnze.hatenablog.com/entry/2026/08/01/043000)の「捕獲報酬のみ」実験、[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)の「MoE を均等化しても待機型に戻る」実験、[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)の「ハンガリアンでも居座る」実験は、
同じ教訓を示している。

> エージェントが待つのは、**その観測と報酬の下で待つことが合理的だから**である。

[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)の考察は明快だ。pursuit_v5 では獲物が自ら近づいてくるため、能動的に探索するより
待機して包囲網を維持する方が累積報酬が高くなる可能性がある。もしそうなら、
「待つな」と罰するのは症状への対処であって、原因への対処ではない。

### 8.2 指標は改善し、行動は悪化しうる

[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)の比較は、評価の難しさをよく示している。

- 全期間平均では Reward +6.9%、捕獲数 +11.8% と「改善」。
- しかし直近10エピソードでは Reward 180.3 → 152.8 と悪化。
- 動画では居座りが再発。

**平均値は学習の途中経過を混ぜる。** 学習曲線が単調でない場合、全期間平均の改善は
「最終的な方策が良くなった」ことを意味しない。比較するときは、

- 同じ update 区間・同じエピソード数で切る
- 直近 N エピソードを見る
- 報酬・捕獲数・エントロピーに加えて、**行動指標**（捕獲間隔、次ターゲットまでの時間、
  探索カバレッジ、停滞時間）を見る
- 可能なら動画で定性確認する

### 8.3 評価の原則

1. **行動が ground truth。** 報酬が上がっても、望む行動が出ていなければ失敗である（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。
2. **学習曲線は「途中」と「終端」を分けて読む。** 終盤の崩れは、報酬スケール・学習率・
   クリッピング・エントロピー係数の相互作用を疑う。
3. **指標を目的化しない。** 捕獲数を上げるために待つなら、捕獲数は増えるがタスクの質は下がる。
   目的関数と評価指標を分離する。

## 9. 教訓7 — 組合せ最適化は RL に任せすぎない。ただし条件を合わせる

### 9.1 階層型設計という発想

[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)のハンガリアン法は、結果としては失敗だったが、**設計思想としては最も洗練されている**。
「誰がどの獲物を追うか」は本質的に割当問題（組合せ最適化）であり、End-to-End の RL に
任せると、重複追跡や放置ターゲットに陥りやすい。そこで、

- **割当**は `scipy.optimize.linear_sum_assignment` で数学的に解く
- **低レベルの追跡・包囲**だけを RL に学ばせる

という役割分担にする。これは「学習に任せる部分」と「アルゴリズムで解く部分」を分ける
階層型設計であり、MARL の実務で非常に有効なパターンである。

### 9.2 失敗から学ぶ3つの条件

しかし今回の実装は、次の3点で環境の成功条件と噛み合っていなかった（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。

1. **割当の粒度が違う** — 1体1獲物ではなく、**獲物の周囲の包囲スロット**（上下左右の空きマス）を
   割り当てるべきだった。Pursuit の捕獲は2〜4体で1体を囲むことで成立する。
   1体1獲物では「手分けを強くしすぎて、誰も包囲を完成できない」。
2. **コストが現実と違う** — マンハッタン距離は障害物も混雑も無視する。BFS/A* の経路長、
   味方の集中による混雑コスト、担当変更のコストを入れるべきだった。
3. **状態の更新が壊れている** — `cycles` 属性の不存在により、割当が開始時に固定され、
   しかも座標をキャッシュしていたため、動く獲物を追えていなかった。獲物IDを保持し、
   現在座標は毎ステップ読み直す必要がある。

さらに、割当が頻繁に入れ替わる**チャタリング**への対策（ヒステリシス、再割当間隔、
持ち替えコスト）も設計課題として挙げられている。

### 9.3 階層型設計の原則

1. **組合せ構造を持つ部分は、明示的に解いた方が安定する。** ただし
   **環境の成功条件と目的関数を一致させる**。囲むタスクなら「獲物」ではなく「包囲位置」を割り当てる（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。
2. **外から与えた構造は、学習を助けるが、学習を代替しない。** 割当は「誰がどこを目指すか」を決めるが、
   「どう追い込むか」「どう逃げ先を塞ぐか」は RL の仕事である。
3. **チャタリングを設計する。** 割当の頻繁な切り替えは、方向の頻繁な変更を強制し、
   かえって非効率になる。前回の担当を維持するコスト、再割当間隔、強制再割当の条件を決める。
4. **特権情報を使うなら、その分だけ Actor の学習を補助していることを自覚する。**[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)の記録は
   「モデルが本来学ぶべき連携の一部を外から補助している」と正しく位置づけている。

## 10. 教訓8 — 実験を壊すのは、アルゴリズムより「実装の前提」

このディレクトリで最も実務的に価値が高いのは、おそらくこの節である。失敗の多くは
アルゴリズムの選択ではなく、**環境やライブラリに対する前提の誤り**だった。

| 事象 | 見落としていた前提 | 結果 | 対策 | 出典 |
|---|---|---|---|---|
| Critic loss がほぼ0 | `shared_reward=True` では `returns.mean(dim=1)` がほぼリターンそのもの | Critic が定数を学習し、Advantage が機能しない | グローバルリターンを正しく学習させる | [第6回](https://yoshishinnze.hatenablog.com/entry/2026/06/27/043000) |
| 捕獲後も4人で止まる | `allies_in_view == 4 and has_moved` の分岐で、4人ちょうど＆停止が**どちらにも該当しない** | 停滞ペナルティの抜け穴 | 人数条件に関わらず停止に罰 | [第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000) |
| ハンガリアンが効かない | Pursuit に `cycles` 属性は存在しない（`steps` / `frames`） | 割当が開始時に固定、古い座標を追い続ける | 内部環境の `frames` を使う。座標でなくIDを保持 | [第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000) |
| 次元不一致で落ちる | 方向ベクトル追加後、`obs_dim`・スライス境界・融合層の次元 | 実行時エラー、または静かな混線 | 生成側と参照側を同時に修正 | [第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000) |
| PPO 更新で学習が破綻 | rollout 時のデコード順序を保存していない | causal mask と行動の対応がずれる | `order` をバッファに保存し更新時に再生 | [第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000) |
| 学習前半だけ性能低下 | チェックポイントの `feature_fuse.weight` 形状変更（64×128→64×130） | オプティマイザが初期化される | 形状変更時は学習率・再開方針を記録 | [第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000) |
| 報酬比較ができない | 報酬全体を 1/5、ハイブリッドを 0.05 倍に再スケール | 横断比較が無意味になる | 捕獲数・エントロピー・行動で比較 | [第10回](https://yoshishinnze.hatenablog.com/entry/2026/07/25/043000) / [第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000) |

ここから導けるチェックリストは次の通り。

1. **環境のソースを読む。** 属性名、終了条件、捕獲条件、報酬の定義は、ドキュメントではなく実装で確認する。
2. **報酬の分岐は全ケースを列挙する。** `if/elif` の「どの条件にも入らない」ケースが抜け穴になる（[第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000)）。
3. **次元を変えたら、生成・参照・保存の3箇所をgrepする**（[第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000)）。
4. **確率モデルの順序・マスク・バッファは、rollout と update で同一であることをテストする**（[第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000)）。
5. **内部指標をログに出す。** Critic loss、Advantage、エントロピー、expert 利用率、ゲート飽和率、
   割当の切り替え回数。行動だけ見ていても原因は分からない（[第14回](https://yoshishinnze.hatenablog.com/entry/2026/08/22/043000)、[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)）。
6. **報酬スケールを変えたら、比較用の指標を切り替える。** 報酬の絶対値は使わない。

## 11. 次にやるなら — 第18回の地点からのロードマップ

[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)の総括と改善案を、優先順位付きで整理する。

### 最優先: 実装の前提を直す

1. `_get_current_cycle()` を内部環境の `frames` ベースに修正する。
2. 割当は獲物の**ID**を保持し、現在座標は毎ステップ取得する。
3. 獲物が捕獲された／一定時間距離が縮まない／エージェントが停止している、のいずれかで強制再割当。

### 次: 割当の粒度を環境に合わせる

4. 獲物そのものではなく、**包囲スロット**（獲物の上下左右の空きマス）を割り当てる。
5. 全獲物を一度に候補にせず、先に捕獲対象を数体に絞ってからスロットを割り当てる（分散しすぎ防止）。
6. コストをマンハッタン距離から **BFS/A* の経路長 + 混雑コスト + 持ち替えコスト** に変更する。
7. 再割当間隔またはヒステリシスでチャタリングを抑える。

### さらに: 観測と評価を整える

8. 獲物の速度・進行方向を観測に追加する、GRU などで時間方向の記憶を持たせる、
   未来位置予測を補助タスクにする（「まごまご」対策。[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。
9. 捕獲間隔（1体目→2体目までのステップ数）、探索カバレッジ、停滞時間をログに追加する。
10. 報酬はポテンシャルベース整形を基本にし、チーム／個人の比率をアニールする（[第12回](https://yoshishinnze.hatenablog.com/entry/2026/08/08/043000)）。
11. 必要ならカリキュラム学習（獲物数を減らす、視界を広げる）や模倣学習を検討する。

### 研究レベル

12. 割当を RL 自身に学習させる（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)の記録が「理想」と表現している方向）。
13. 明示的な通信チャネル（メッセージ Passing）の導入。
14. MoE の専門化を「状況の切り替え」に結びつけるための、補助タスク（次に狙う獲物の予測など）。

## 12. まとめ — MARL で重要な5つの原則

このディレクトリの試行錯誤は、次の5つに集約できる。

### 原則1: 報酬は目的、個人報酬は勾配

チーム報酬だけではサボりが合理的になり、個人報酬だけでは局所解に落ちる（[第7回](https://yoshishinnze.hatenablog.com/entry/2026/07/04/043000)、[第8回](https://yoshishinnze.hatenablog.com/entry/2026/07/11/043000)）。
報酬を足したら、必ず「一番安い抜け道」を探す。囲み続ける、往復する、待つ、の3つは特に警戒する（[第11回](https://yoshishinnze.hatenablog.com/entry/2026/08/01/043000)）。

### 原則2: 観測が天井を決める

「望ましい行動」を罰する前に、その行動を選ぶのに必要な情報が入力にあるか確認する（[第15回](https://yoshishinnze.hatenablog.com/entry/2026/09/05/043000)）。
方向情報がなければ探索報酬は徘徊への報酬になる（[第17回](https://yoshishinnze.hatenablog.com/entry/2026/10/03/043000)）。全員に同じ情報を渡すなら、
同時に「誰が何を担当するか」の差を作る仕組みを入れる（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。

### 原則3: 構造は仮説、理論は保証ではない

CNN → Transformer は質的な跳躍を生んだが（[第9回](https://yoshishinnze.hatenablog.com/entry/2026/07/18/043000)）、MAT は決定的な改善をもたらさなかった（[第11回](https://yoshishinnze.hatenablog.com/entry/2026/08/01/043000)）。
アーキテクチャは仮説空間を広げるが、目的関数と観測が間違っていれば、より効率的に間違った解へ収束する。
**帰納バイアスをタスクの要求（関係・座標・順序）に合わせる**。

### 原則4: 協調は「誰が誰を見るか」の設計

同時決定か逐次決定か、デコード順序を固定するかランダム化するか、ゲートが何を見るか、
同時クリップか個別クリップか（[第13回](https://yoshishinnze.hatenablog.com/entry/2026/08/15/043000)、[第14回](https://yoshishinnze.hatenablog.com/entry/2026/08/22/043000)）。これらはすべて協調の設計変数であり、
**役割の固定化・信号の遮断・道連れ**という形で失敗が現れる。
内部指標（expert 利用率、ゲート飽和率、Advantage）をログに出して監視する（[第16回](https://yoshishinnze.hatenablog.com/entry/2026/09/26/043000)）。

### 原則5: 評価は行動、失敗は前提

指標は改善しても行動は悪化しうる（[第18回](https://yoshishinnze.hatenablog.com/entry/2026/10/10/043000)）。全期間平均ではなく直近 N エピソードと行動指標を見る。
そして、アルゴリズムを疑う前に、環境の属性名、報酬の分岐、次元、順序、マスク、報酬スケールという
**実装の前提**を疑う。このディレクトリの失敗の半分は、そこにあった。
