# 問題

以下は「**中程度の難易度**のマルチエージェント強化学習（MARL）問題」のセットです。

1つの大課題＋バリエーションも付けたので、課題設計として使いやすいと思います。

---

# 【中難易度 MARL 課題】

## **配送ドローン 2体による協調型ピックアップ＆デリバリー問題**

### **概要**

2体のドローンエージェントが、

複数の荷物を **拾う（Pick）→ 指定場所へ運搬（Deliver）** というタスクを協力して行う。

環境は 10×10 グリッド。

荷物はランダムに生成され、それぞれ **Pick座標** と **Deliver座標** を持つ。

---

# **ルール**

### ■ エージェント

* 2体のドローン
* 各ステップで以下の行動が可能
  * 上下左右へ1マス移動
  * その場で待機
  * 荷物の Pick / Deliver

### ■ 状態（State）

各エージェントが観測できるもの：

* 自身の位置 (x, y)
* 自分が持っている荷物 ID（または None）
* 視界範囲内（例：マンハッタン距離 4）の障害物・荷物の位置
* もう1体のエージェントの位置（限定的に観測）

### ■ 報酬（Reward）

* 荷物を Pick → +1
* 荷物を Deliver （成功）→ +10
* エージェント同士が衝突すると −5
* 無駄な移動（目的地方向から離れる）→ −0.1
* タスク完了時 +5 のグローバルボーナス

### ■ 目的

2体が協力して「全ての荷物の配送タスクを最短で終わらせる」こと。

協力が必要な理由：

* 距離の遠い荷物があり、単独では時間がかかる
* 衝突リスクがあり、他者の行動を意識する必要がある
* 同じ荷物を取りに行くと無駄が発生（役割分担が必須）

---

# **難易度が中程度になる理由**

* 協力（Cooperation）が必須
* 自律的な役割分担（Work Sharing）が発生
* 競合行動（同じ荷物に向かう）を避ける必要
* 衝突回避（Multi-Agent Path Finding 成分）
* 観測が部分的（Partial Observability）
* QMix / VDN / MAPPO / MADDPG あたりで解けるレベル

---

# **追加バリエーション（自由に難易度調整可能）**

## ① **動的に湧く荷物バージョン（難易度 ↑）**

一定確率で新しい荷物が出現する。

オンラインタスク割り当てが必要になる。

## ② **エージェント間通信ありバージョン（難易度 ↓）**

1step 1bit だけ通信可能にする

例：

* 「今から○○の荷物を取りに行くよ！」を意思表示

MAPPO で比較的学習しやすくなる。

## ③ **燃料（ステップ制限）あり（難易度 ↑）**

エージェントに行動コストを与え、

最適なルート選択が重要になる。

## ④ **競合型（敵対的）バージョン（難易度 ↑）**

協力エージェント2体 vs 妨害ロボット1体

Stochastic ゲームになり学習が難しくなる。

# MAZeroの問題


MAZero が計算が重い（遅い）主な原因は、**「モデルベース + MCTS + マルチエージェント」** という設計そのものにあります。  
具体的には、以下の4つがボトルネックになりやすいです。


### 1. MCTS の計算コストが高い

MCTS は、**木探索とシミュレーションを繰り返す**ため、計算コストが高いです。

- **シミュレーション回数**：1回の行動選択につき、数十〜数百回のシミュレーションが必要
- **深さ**：将来のステップを何ステップも先までシミュレーションするため、計算量が増える
- **共同行動空間**：マルチエージェントでは共同行動の組み合わせが指数的に増え、  
  探索すべきノード数が爆発的に増加

**影響**：
- 1ステップあたりの計算時間が長くなり、**リアルタイム性が低下**
- 学習ループ全体で見ると、**総計算時間が膨大**になる


### 2. 世界モデルの推論コスト

MAZero は、**世界モデル（遷移モデル + 報酬モデル）** を学習し、MCTS の各ステップで使用します。

- **遷移モデル**：状態 $s$ と共同行動 $\mathbf{a}$ から次の状態 $s'$ を予測
- **報酬モデル**：報酬 $r$ を予測
- **価値ネットワーク**：状態 $s$ の価値 $V(s)$ を推定

MCTS の各シミュレーションでこれらを何度も呼び出すため、**ニューラルネットの推論コストが積み上がります**。

**影響**：
- GPU メモリ使用量が増加
- バッチ処理が難しい（MCTS は逐次的）ため、**並列化が困難**
- モデルが深いほど、1回の推論が重くなる


### 3. 共同行動空間の指数的膨張

マルチエージェント環境では、**共同行動空間が指数的に膨張**します。

- エージェント数 $N$、各エージェントの行動数 $|\mathcal{A}|$ とすると、  
  共同行動数は $|\mathcal{A}|^N$
- MCTS では、**各ノードで共同行動の組み合わせを探索**するため、  
  ノードあたりの計算量が爆発的に増加

**影響**：
- エージェント数が増えると、**計算時間が指数的に増加**
- 大規模環境（SMAC の hard シナリオなど）では、**実用的な計算時間を超える**可能性


### 4. モデル学習とプランニングの二重コスト

MAZero は、**モデル学習**と**MCTS によるプランニング**の両方を行います。

- **モデル学習**：世界モデルを更新するためのバックプロパゲーション
- **プランニング**：MCTS で行動を決定するためのシミュレーション

これにより、**1ステップあたりの計算コストが「モデルフリー手法の数倍〜数十倍」**になることがあります。

**影響**：
- 学習ループが遅くなり、**同じ経験数でも学習に時間がかかる**
- 大規模環境では、**計算資源の制約がボトルネック**になる


### 5. 実装上のボトルネック

実装次第では、以下の点も計算を重くする原因になります。

- **Python の逐次処理**：MCTS のシミュレーションが Python ループで実装されていると、  
  GPU の並列性を活かせず遅い
- **メモリコピー**：状態や行動のテンソルを CPU/GPU 間で頻繁にコピーすると遅延が発生
- **ログ出力や可視化**：デバッグ用の出力が多すぎると I/O がボトルネックになる


### 6. 対策（軽量化の方向性）

MAZero を軽量化するには、以下のような対策が考えられます。

1. **MCTS のシミュレーション回数を減らす**：
   - シミュレーション回数や深さを調整
   - 早期打ち切り（Early Stopping）を導入

2. **モデルの軽量化**：
   - 世界モデルや価値ネットワークの層数を減らす
   - パラメータ数を削減（Pruning, Quantization）

3. **並列化**：
   - MCTS のシミュレーションをバッチ処理で並列実行
   - 複数の環境インスタンスを並列に実行（Vectorized Environment）

4. **近似手法の導入**：
   - MALinZero のように、**低次元表現で MCTS を行う**手法を検討[OpenReview](https://openreview.net/forum?id=8e363493ff9d9b3fa837f8d6bb3198fa13ba65f4)
   - 共同行動空間を削減（行動の抽象化や階層化）


### 7. まとめ

MAZero が重い主な原因は：

- **MCTS のシミュレーション回数と深さ**による計算コスト
- **世界モデル・価値ネットワークの推論コスト**
- **共同行動空間の指数的膨張**
- **モデル学習とプランニングの二重コスト**
- **実装上のボトルネック（逐次処理、メモリコピーなど）**

これらを改善するには、**MCTS の設定調整、モデルの軽量化、並列化、近似手法の導入**などが有効です。[arXiv](https://arxiv.org/abs/2405.11778)[OpenReview](https://openreview.net/forum?id=8e363493ff9d9b3fa837f8d6bb3198fa13ba65f4)
