目次

    本日はずっと続いている迷路を解く問題です。 前回ゴールまでは出来るようになりましたが、スムーズにゴールに到達せず、うろうろする癖がありました。 うろうろしないで、安定してゴールできるようにしていきたいということで改善のトライアルを行います。

    現状課題

    解くたびにランダムに構造が変化する迷路を強化学習を行ったエージェントによりゴールを目指すという目標に向けて進めてきました。 現状はゴールは目指し、また、ゴールはしてくれるけど、毎回ゴールできるわけではなく、別の場所に行ってうろうろということもあります。 また、不得手な迷路があるようで、ダメなときはトコトン変なところをうろうろすることがあります。 安定して、うろうろしないようにできないかということで改善に取り組みます。

    改善案の検討

    モデルの表現力見直し

    モデルが少し小さいため、視覚で見えている位置関係から分析できるパターンに制限がかかってる可能性を感じました。この辺りが見たことないパターンの迷路だと?となっているのでは、ということが想定する原因です。 ですのでモデルの表現力を見直します。

    今回のケースではモデルの表現力はモデルのサイズと置き換えてください。 モデルのサイズにはパラメータが3種類(num_layers, dim_feedforward, d_model)あります。

    それぞれのパラメータについて変更することによる想定効果を整理しました。

    変更 何が変わるか このタスクへの適合度
    num_layers 2→3,4 「壁の情報→隣接マスとの関係→さらにその先との関係」という多段階の関係推論の深さが増す 高。迷路の経路探索は本質的に「Aの隣にBがあり、Bの隣にCがあり…」という多ホップの関係を辿る問題。フルAttentionにした今、層を重ねるほど間接的な関係(マスAとマスDの関係、など)をより高次に表現できる
    dim_feedforward d_model×2→×4 各トークン（各マス）が個別に持てる非線形変換の表現力が増す 中。マス単体の特徴表現は5チャンネル(壁/S/G/エージェント/距離)とかなり単純なので、これ以上複雑にする余地は少ない
    d_model 64→96,128 全体の次元数が増え、Attentionのquery/key/valueの表現力も上がる 低〜中。25マス+CLSという小さいトークン数に対し、既に64次元はかなり余裕がある。次元を増やしても、それを活かすだけの多様な入力パターンが少ない

    迷路の探索という問題の本質は「情報の幅」より「関係の深さ（何ホップ先まで考慮できるか）」なので、層を増やす方が構造的に噛み合っています。 上記の中から取り組むのであれば num_layers とします。 現状はレイヤ数が2なので、倍の4にしてみます。

    迷路の問題で解けなかった問題を集中的に出題

    問題の中で得意不得意がありそうな傾向でした。(ゴールが壁に囲まれている場合、ゴール近くをうろうろする、など) このため、不得意問題を集中的に解かせて苦手な問題への対応力を増すことを考えてみようかと思います。 (これは強化学習の分野でPrioritized Level Replayと呼ばれる手法に近い考え方です。)

    Prioritized Level Replay (PLR) Prioritized Level Replay (PLR) は、強化学習（特に手続き型生成環境やマルチタスク環境）において、「エージェントにとって学習価値が高い（＝難しすぎず易しすぎない）レベル（環境のシード値など）を優先的に再学習（Replay）させる」ことで、サンプリング効率と汎化性能を大幅に向上させる手法です。 DeepMind や NYU などの研究チーム（Minqi Jiang, Jakob Foerster 等）によって提案されました。 1. なぜ PLR が必要なのか？（背景と課題） プロシージャル生成（ProcGen）された迷路やミニゲームなどの環境では、ランダムにレベル（シード値）を生成して学習させると以下のような問題が生じます。

    • 無駄なサンプリング: 易しすぎるレベル（瞬時に解ける）や、難しすぎるレベル（ランダム探索では絶対に解けない）に学習計算リソースを費やしてしまう。
    • 忘却の発生: 過去にクリアできたレベルや、あと少しで攻略できそうだったレベルの復習機会がランダムサンプリングでは乏しい。 PLR は、「すでに経験したレベルの履歴（Level Buffer）」 を保持し、エージェントの現在の習熟度に応じて「今まさに復習すべきレベル」を厳選して提示します。 2. PLR の基本アルゴリズムと仕組み PLR の各トレーニングステップでは、一定の確率 PreplayP_{\text{replay}}Preplay​（例: 0.5）で動作を分岐させます。
    1. Replay（復習モード / 確率 PreplayP_{\text{replay}}Preplay​）:
    • バッファ内に保存された過去のレベルの中から、「スコア（TD誤差など）」が高いレベルを優先的に選択して再プレイします。
    1. Unexplored（新規探索モード / 確率 1−Preplay1 - P_{\text{replay}}1−Preplay​）:
    • まだ見ぬ完全に新しいシード値（新規レベル）をランダム生成してプレイします。
    • プレイ後のデータ（スコアや軌跡）を評価し、レベルバッファを更新・保存します。 3. レベルの優先度（Score）はどう決めるか？ PLR の核心は「どのレベルを『優先すべきレベル』とみなすか」です。主に以下の指標（学習プログレスや価値の推定誤差）が使われます。
    • Value Loss / TD Error（価値関数の予測誤差）:
    • エージェントが「状態の価値（到達可能性や期待報酬）」を正確に予測できていないレベル。
    • 予測誤差が大きいレベル＝エージェントがまだ理解しきれておらず、学習の伸びしろ（Learning Progress）が大きいレベルとみなします。
    • Max / Mean TD Error:
    • エピソード内での最大TD誤差や平均TD誤差をレベルの優先度スコアとして設定します。 4. 主な派生手法・進化形 PLR は単体でも強力ですが、以下のような発展型が存在します。
    • Robust PLR (R-PLR):
    • 過去の評価値（Score）の古さ（Staleness）による偏りを補正し、古くなったレベルのスコアを再評価・更新する機構を備えた堅牢版。
    • Robust Prioritized Level Replay with Robust Value Learning (Robust PLR / ACCEL):
    • ACCEL (Adversarial Curriculum Through Evolving Levels) などに発展し、生成型カリキュラム学習（Domain Randomization や 敵対的環境生成）と組み合わせて、難易度を動的に編集・進化させるアプローチへ応用されています。

    このため、「毎回完全ランダムな新しい迷路」ではなく、固定サイズの迷路プールを持ち、そのプール内で正解率が低い迷路ほど出題確率を上げる、という設計にします。

    まず設計を説明します。

    設計方針

    1. 迷路プール：N個(既定100個)の迷路を保持。各迷路ごとに直近の成功/失敗履歴を記録
    2. 出題確率：苦手度スコア = 1 - 直近成功率 に比例した確率でプールから選ぶ（不得意なものほど出やすい）
    3. 新規迷路の注入：一定確率でプール外の完全新規ランダム迷路も混ぜる（プール内だけに過学習しないため。苦手な迷路パターン自体を汎化して克服してほしいので、固定10問だけを完璧にする、という状態は避けたい）
    4. プールが満杯なら、最も得意（成功率が高い）迷路を追い出して新しい迷路と入れ替える

    まずMazeEnvに「特定の迷路をそのまま設定する」機能を追加します。次に、迷路プールを管理するMazePoolクラスを新規作成します。次にtransformer_ppo.pyのtrain()にこのプールを統合します。Now train()にプールベースの出題ロジックを追加します。次に、エピソード終了後にプールへ結果を記録する処理と、プールの統計ログを追加します。動作確認します。正常に動作しています(プールが苦手な迷路IDを追跡し、優先的に出題されていることが確認できます)。ファイルを出力します。

    実装

    MazePoolクラス： 固定サイズの迷路プールを管理し、各迷路の直近成功率から「苦手度スコア（1 - 成功率）」を計算、それに比例した確率で出題する迷路を選びます。

    MazeEnvクラス： reset()にmaze_override引数を追加。(maze, start, goal)を渡すと、ランダム生成をスキップしてその迷路をそのまま再現できるようにしました(プールから取り出した迷路を再出題するために必要)。

    TransformerActorCriticクラス： train()にuse_prioritized_replay=Trueで有効化できるロジックを追加：

    • プールが埋まるまで、あるいは確率pool_new_maze_prob(既定20%)で新規ランダム迷路を生成してプールに追加
    • それ以外は、プールから苦手度に応じた確率で迷路を選んで出題
    • エピソード終了後、その迷路の成功/失敗をプールに記録
    • ログにプール全体の成功率と苦手Top5の迷路ID・成功率・試行回数を表示
    • use_curriculumと併用可能：新規注入する迷路の難易度上限をcurriculumのcurrent_max_distanceに合わせられます

    使い方

    実装したコードを実行する場合は以下のようにします。

    episode_rewards, success_history = agent.train(
    num_episodes=2000,
    use_prioritized_replay=True,
    pool_size=100,           # プールに保持する迷路の数
    pool_history_len=10,     # 1迷路あたり直近何回分の成功/失敗で判定するか
    pool_new_maze_prob=0.2,  # プール満杯後、新規ランダム迷路を混ぜる確率
)

# 学習後、プールの中身を詳しく見たい場合
print(agent.maze_pool.stats(top_k=10))

    注意点・トレードオフ

    • プールに"べた覚え"するリスク：pool_sizeが小さすぎたりpool_new_maze_probが低すぎると、その少数の迷路パターンを個別に記憶してしまい、プール外の未知の迷路への汎化が犠牲になる可能性があります。pool_size=100程度、new_maze_prob=0.2前後から始めて、必要に応じて調整してください。
    • 「苦手な迷路」＝「本質的に難しい迷路」とは限らない：たまたま運悪く数回失敗しただけの迷路も一時的に「苦手」扱いされます。pool_history_lenを大きめ(15〜20)にすると、ノイズに惑わされにくくなります。
    • プール自体は学習経過情報なので保存されません。学習を再開する場合はプールも作り直しになります（必要であればpickle等での保存機能も追加できます）。

    学習

    学習推移

    学習の推移を可視化します。 青が前回、オレンジが今回です。 オレンジは不得手な問題を優先して解くことになるため報酬の平均は前回よりも悪くなりました。 やはり、不得手な分野がありそうだという感触です。

    更にゴールを出来た確率をトレースしてみました。 こちらも前回に比べると低下傾向です。

    感触では不得手なゴールを解決するというところまではいってないか、という感じがします。

    学習後の動作

    学習したエージェントで実際にランダムに変わる迷路を解かせてみます。 3つ目は、回り込む問題で、前回なかなか解けなかった問題でした。 解けるようにはなったか・・・、という思いです。

    但し、うろうろは未だします。

    総括

    以下、今回の改善実験の内容と結果を総括します。

    1. 改善の狙いと方針

    目的

    • 「毎回ランダムに構造が変わる迷路」を強化学習エージェントに解かせるタスクで、
      • ゴールはするが「毎回ゴールできるわけではない」
      • 不得手な迷路があると、変な場所をうろうろしてしまう
      • うろうろせず、安定してゴールできるようにしたい

    2つの主な改善方針

    1. モデル表現力の見直し（モデルサイズの拡大）

      • 迷路探索は「A→B→C…」という多ホップの関係推論が本質であるため、
      • 層数 num_layers を 2 → 4 に増やし、多段階の関係推論を強化した。

    2. 不得意な迷路を集中的に出題（Prioritized Level Replay に近い発想）

      • 完全ランダム生成ではなく、固定サイズの迷路プールを用意。
      • 各迷路ごとに直近の成功率を記録し、
        • 「苦手度スコア = 1 − 成功率」に比例した確率で出題
        • 一定確率で新規ランダム迷路も混ぜる（プール外への汎化を維持）
      • プールが満杯のときは、最も得意な迷路を追い出して新規迷路と入れ替える。

    2. 実装の概要

    MazePool クラス

    • 固定サイズ（既定100個）の迷路プールを管理。
    • 各迷路ごとに直近の成功/失敗履歴を保持し、苦手度スコアを計算。
    • そのスコアに基づいて出題確率を調整。

    MazeEnv クラス

    • reset(maze_override=...) を追加し、特定の迷路をそのまま再現できるようにした。
    • これにより、プールから取り出した迷路を「同じ状態で」再出題可能。

    TransformerActorCritic.train()

    • use_prioritized_replay=True で有効化。
    • 新規ランダム迷路を混ぜる確率 pool_new_maze_prob（既定0.2）を設定。
    • エピソード終了後にその迷路の成功/失敗をプールに記録。
    • ログに
      • プール全体の成功率
      • 苦手Top5の迷路ID・成功率・試行回数 を出力。

    3. 学習結果の振り返り

    報酬推移・成功率推移

    • 報酬の平均値は前回（青）より今回（オレンジ）の方が悪化。
    • ゴール達成率も前回より低下傾向。
    • これは「不得意な迷路を優先的に出題する」ため、
      • 学習中に難易度の高い迷路を多く解くことになり、
      • 報酬や成功率が一時的に悪化するのは設計通り。

    学習後の動作観察

    • ランダムに変化する迷路を解かせた結果：
      • 以前は解けなかった「回り込みが必要な迷路」が解けるようになったケースがある。
      • しかしうろうろは依然として残っている。
      • 以前よりは安定したが、「完全にうろうろをなくす」には至っていない。

    4. 現状の評価と課題

    良い点

    • モデル層数を増やし、迷路の多ホップ関係を扱う能力を強化した。
    • Prioritized Level Replay 的な設計により、
      • 不得意な迷路を重点的に学習する仕組みを導入。
      • 迷路プールと苦手度スコアに基づく出題ロジックが動作している（ログで確認済み）。
    • 一部の「以前は解けなかったパターン」が解けるようになった。

    残る課題

    • うろうろ行動が完全には解消されていない
      • 不得意な迷路を多く出題した結果、学習中に難易度の高い迷路を多く経験しているにもかかわらず、
      • それらを「安定して」解けるレベルには達していない。
    • 迷路プール設計のトレードオフ
      • pool_size や pool_new_maze_prob の設定によっては、
        • 少数の迷路に「べた覚え」してしまい、未知の迷路への汎化が弱くなるリスクがある。
      • 苦手度スコアは「直近の成功率」に基づくため、
        • たまたま数回失敗しただけの迷路も一時的に「苦手」扱いされ、ノイズが混入しうる。

    5. まとめ

    • モデル層数の増加と不得意迷路を優先的に出題する仕組みを導入したことで、
      • 学習中に難易度の高い迷路を多く経験させ、
      • 一部の「以前は解けなかったパターン」が解けるようになった。
    • 一方で、
      • 報酬・成功率は一時的に悪化し、
      • うろうろ行動はまだ完全には解消されていない。
    • 現状は「不得意な迷路を認識し、重点的に学習する枠組み」は整ったものの、
      • その学習を安定した行動に結びつける段階には至っていない、という段階と評価できます。

    今後の方向性としては、

    • 迷路プールのパラメータ（pool_size, pool_history_len, pool_new_maze_prob）の調整
    • モデル構造のさらなる見直し（層数・Attentionヘッド数・学習率など）
    • 行動価値の予測誤差（TD誤差）をより精緻に使った「本当に学習価値の高い迷路」の選定 などが考えられます。
